# LLM 与智能体在补货系统中的定位

## 结论

对于数据口径统一、业务规则明确、库存约束严格的即时零售补货场景，LLM 不是核心必需组件。需求预测、P50/P90、目标库存、建议订货量、预算约束、审批判断和执行写入，都应由结构化数据、专用预测模型、确定性策略和约束校验完成。

本项目不是 LLM 补货系统，而是一套可插拔、可验证、可审计的智能补货决策流水线。

## 为什么不把 LLM 放进核心链路

补货决策要求相同输入得到可复现结果，所有约束可验证，失败原因可定位，运行记录可回放。LLM 的自然语言生成能力不能替代这些要求，反而可能引入输出漂移、约束遗漏、预测区间缺乏校准、调用成本和审计复杂度。

如果业务人员无法理解标准化结果，优先应改进指标定义、原因码、计算证据、界面和业务培训，而不是增加解释型 Agent。

## 透明的决策结果

```json
{
  "forecast_p50": 12.4,
  "forecast_p90": 18.7,
  "recommended_order_qty": 15,
  "expected_cost": 60,
  "stockout_risk": 0.12,
  "approval_required": false,
  "constraint_status": "passed",
  "decision_id": "abc-123",
  "reason_codes": ["below_target_inventory", "lead_time_and_review_covered", "max_spend_checked"]
}
```

这些字段比临时生成的自然语言更适合测试、审计、回放和跨系统传递。

## LLM 可以放在哪里

只有在存在明确收益时，才考虑把 LLM 作为外围可选能力：

- 读取供应商邮件、合同、会议纪要等非结构化信息；
- 辅助跨系统查询和信息汇总；
- 生成字段映射或规则配置草稿，由人工确认后固化；
- 归纳异常工单和运营反馈；
- 提供自然语言查询入口。

这些能力不能修改确定性的预测、订货量、预算约束、审批状态或执行结果。

## 推荐边界

```text
数据适配器 -> 预测模型 -> 补货策略 -> 约束校验 -> Decision -> 审批 -> 执行器 -> 审计记录

LLM（可选）只读取结构化结果或外围非结构化资料
```

Agent 不应直接生成最终订货量，也不应直接写入 ERP、WMS 或 OMS。任何外部动作都必须经过 Schema 校验、业务约束和权限审批。

## 对本项目的影响

当前主线应继续投入在数据适配器、数据质量、预测与分位数校准、补货策略、业务约束、历史回放、评估指标、决策记录和受控执行。LLM/Agent 只作为长期可选扩展，不应成为项目的主要卖点，也不应为了“看起来智能”而进入补货核心路径。
