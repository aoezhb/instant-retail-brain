# 门店与仓点为什么必须分开

即时零售系统中，门店和仓点经常在早期数据里表现为一对一：一个门店对应一个库存地点，订单也由这个地点履约。此时把两者写成同一个编号看起来更简单，但这种做法会把销售关系和库存关系混在一起。一旦增加共享仓、前置仓、多门店履约或拆单，原有数据就很难继续使用。

最简洁的区分方式是：

- 门店回答“需求在哪里发生、由谁经营”。
- 仓点回答“库存在哪里、由哪里拣货和履约”。
- 经营主体回答“这些门店和仓点属于哪套经营与核算体系”。

## 三类对象承担不同职责

| 对象 | 主要记录 | 常见问题 |
|---|---|---|
| 经营主体 | 组织归属、经营规则、核算口径 | 哪个主体承担采购、库存和损益 |
| 门店 | 销售、客群、选品、价格、活动 | 哪个销售地点产生了需求 |
| 仓点 | 可用库存、在途、预留、欠单、履约范围 | 哪个库存地点负责满足需求 |

门店是需求观察口径，仓点是库存和履约口径。即使它们现在一一对应，也不代表它们是同一个对象。

## 一对一关系为什么仍然要单独记录

业务关系会变化，而对象身份应保持稳定。

~~~mermaid
flowchart LR
    S1[门店 A] --> N1[仓点 1]
    S2[门店 B] --> N1
    S3[门店 C] --> N2[仓点 2]
    S3 -.特殊时段.-> N1
~~~

常见变化包括：

1. 一个前置仓服务多个线上门店。
2. 一个门店根据距离、库存或运力切换履约仓点。
3. 同一商品由不同仓点拆单履约。
4. 门店关闭但仓点继续服务其他门店。
5. 不同经营主体使用相同的局部门店编号或仓点编号。

如果最初就把门店编号当作仓点编号，这些变化通常需要修改订单、库存、预测和历史记录中的主键，而不只是增加一条关系记录。

## 混用后会出现什么问题

### 需求和库存无法正确汇总

门店预测描述的是销售需求，仓点补货需要的是该仓点需要承担的合计需求。一个仓点服务多个门店时，必须先根据门店到仓点的关系汇总，再计算补货量。

### 库存容易重复计算

如果多个门店共享同一仓点，却在每个门店下复制一份库存，同一批库存会在计算中出现多次，造成虚假的可售量。

### 历史变化无法表达

门店切换履约仓点时，销售历史仍属于原门店，库存和履约记录则属于当时使用的仓点。只有分别保存两种身份，历史回放才能保留当时的真实关系。

### 决策对象不清楚

补货决定需要指出库存进入哪个仓点；选品和价格建议往往针对门店。只保留一个编号时，接收动作的对象容易被误解。

## 本仓库如何表示

项目分别定义 <code>BusinessUnit</code>、<code>Store</code>、<code>FulfillmentNode</code> 和 <code>StoreNodeBinding</code>。门店与仓点的对应关系是一条独立记录，而不是通过编号相等来推断。

运行时商品键为：

~~~text
ItemKey = (
    business_unit_id,
    store_id,
    node_id,
    sku_id,
)
~~~

订单需求、库存、协变量、模型输出和决策均保留这组身份。这样可以做到：

- 相同门店编号出现在不同经营主体时不会相互覆盖。
- 同一门店切换仓点时可以保留不同记录。
- 门店级预测可以明确映射到仓点级补货。
- 决策记录可以同时说明需求来源和履约位置。

<code>RetailDataHandler</code> 会检查需求、库存和协变量是否使用一致的商品键，并从有效数据中生成 <code>StoreNodeBinding</code>。

## 从门店预测到仓点补货

实际计算应明确预测结果描述的是门店还是仓点：

~~~mermaid
flowchart LR
    A[门店 SKU 需求预测] --> B[读取门店与仓点关系]
    B --> C[按履约比例或规则分配]
    C --> D[汇总仓点需求]
    D --> E[结合仓点库存状态]
    E --> F[生成仓点补货建议]
~~~

当前示例的 <code>forecast_scope</code> 为 <code>store</code>，并使用一店一仓的合成数据，因此没有实现复杂的分配比例。客户项目若存在共享仓或动态路由，需要在仓点补货前增加分配和汇总步骤。

## 建议的数据使用规则

1. 销售和需求事实以门店为主要观察对象。
2. 实物库存、在途、预留和欠单以仓点为主要记录对象。
3. 门店与仓点关系单独保存，并带有效时间。
4. 补货动作必须明确目标仓点。
5. 门店策略和仓点策略分别计算，不用一个编号代替两种对象。
6. 聚合前保留经营主体，避免不同主体的局部编号碰撞。
